# Six AI Archetypes deck: claims checked against the NovaMart traces

_Generated by `backend/scripts/validate_deck_claims.py` from the Category 1 ablation (`backend/experiments/cat1_ablation/runs.jsonl` + `backend/replays/cat1_ablation_summary.json`), `backend/replays/cat2_golden_replays.json`, the Category 2 blind-judge quality summary (`backend/replays/cat2_quality_summary.json`), the Category 3 quality rerun (`backend/experiments/cat3_quality/runs.jsonl` + `backend/replays/cat3_quality_summary.json`), the Category 4 quality rerun (`backend/experiments/cat4_quality/runs.jsonl` + `backend/replays/cat4_quality_summary.json`), the Category 5 ablation (`backend/experiments/cat5_ablation/runs.jsonl` + `backend/replays/cat5_ablation_summary.json`), the Category 6 fair rerun (`backend/experiments/cat6_fair_rerun/runs.jsonl` + `analysis/cat6_fair_rerun.json`) and `backend/traces/`. Re-run the script after re-capturing replays._

These experiments compare system designs (what is asked for, how much context is sent, caching, tools, routing between model sizes) in one synthetic lab setup; the results describe those configurations on these tasks and are not an assessment of any model.

## How the data was de-duplicated

`backend/traces/` holds **1074 trace files** but only **244 distinct canonical runs**. 624 files are replay-mode copies written each time the UI served a golden replay; one run appears up to 30×. Averaging the trace index weights each run by how often it was viewed, and it mixes in older captures with different `max_tokens` settings.

Only the newest seed trace per (category, model, pattern, item) counts as canonical; older seeds for the same slot, such as the first Category 3 and Category 6 captures, and replays of them are counted as superseded captures.

**Unit of analysis:** one canonical run per (item × rung), taken from the current golden-replay files, which match the seed traces one-to-one. Categories 1, 3, 4, 5 and 6 are the exceptions. Category 1 uses all 252 ablation runs (7 versions × 12 items × 3 repeats, n=36 per version); its golden replays are repeat 0 of the four versions the app runs. Category 3 uses all 18 quality-rerun records (3 rungs × 2 sessions × 3 repeats, n=6 per rung); its golden replays are repeat 0 of every rung. Category 4 uses the 24 quality-rerun sessions in each version's current answer format (4 rungs × 2 corpus sizes × 3 sessions of 8 questions, 192 answers, n=24 per row), and shows the retrieval versions' 12 sessions with the original answer instructions as *before* rows; its golden replays are repeat 0 of the three app rungs at the 7-document corpus. Category 5 uses the 198 pooled ablation runs (6 versions × 11 invoices × 3 repeats, n=33 per version) and reports the 18 runs on the invoice where the policy gate disagrees with the manual separately; its golden replays are repeat 0 of the three versions the app runs, on inv-01..03. Category 6 uses all 60 fair-rerun records (4 arms × 3 incidents × 5 repeats, n=15 per arm); its golden replays are repeat 0 of three of those arms. Costs are recomputed per API call from recorded token counts, priced by the model that served the call. The traces' own `finops` blocks are not used, so the results don't depend on how the app priced them.

**Cost views.** *Billed*: cache tokens exactly as the API reported them during capture. *Warm*: every cached-prefix token is a cache read (steady state). *Cold*: the first call per model in each unit writes the prefix. All dollar figures use Anthropic's published rates, which `pricing.py` now matches. The *pre-fix card* column shows the repo's earlier $0.20 Sonnet cache-read rate.

## Issues found in the lab code and data

1. **Trace `finops` is not billed cost.** Category 5 and 6 rollups store a *modelled* cold-cache cost (`_compute_step_cold_warm`) instead of the cache tokens the API returned. This is by design and remains. *Fixed:* the rollups priced all output at Sonnet's $10/MTok (and the seed script priced mixed runs at one model's rates), so some traces had `total_cost_usd` < `output_cost_usd`. All four now use `rollup_multi_call_finops`, which prices each call at its own model's rate.
2. **CpO was zero for failed runs.** *Fixed:* `cpo_*_per_1k_usd` is now `None` for an unverified run, and the portfolio CpO and savings are `None` when a rung has no verified outcomes (`cat6_swarms/runner.py`).
3. **Category 1 write-ups were truncated in the first capture.** 11/12 Sonnet and 8/12 Haiku write-ups hit `max_tokens=2048`, so the naive costs were lower bounds. *Fixed:* the app's write-up cap is now 8,192 and the schema cap 512, as in the ablation, where none of the 252 runs was cut off (write-ups ran 1,227–4,046 output tokens).
4. **Cross-rung cache warming.** Capture order lets later rungs and items read caches warmed by earlier ones (e.g. Category 4 audit-02 read the cache audit-01 wrote in the same session, so it shows zero cache writes). The *billed* column includes this effect; the *cold* column removes it. The Category 6 fair rerun avoids it: each run writes its own cache (a per-run nonce in the cached prefix).
5. **Trace index is not de-duplicated.** `index.jsonl`/`summarize_traces()` average replays, superseded captures and session rollups together. Any dashboard built on it over-weights frequently viewed items.
6. **6 error traces** (Gemini Decision × free-text prose, live, `Connection error`) hold zero tokens and should be excluded from averages.
7. **The first Category 6 capture was biased and has been replaced.** Its shared-bus agents were truncated at `max_tokens=3200`, the capture script rejected and re-ran governed runs whose patches did not pass the sandbox, and the governed patch author had explicit hints and word limits the shared-bus author lacked. The fair rerun (4 arms × 3 incidents × 5 repeats, equal output caps, per-run cold caches, no outcome-based selection, a shared-bus arm with matched instructions) replaces it; the capture script now rejects runs only for infrastructure failures.
8. **AST-SEC-01 false positive (fixed).** The constant-time-comparison check treated a comparison against a module-level scheme-prefix constant (`_SIG_PREFIX = "sha256="`) as a direct signature `==`. Three shared-bus inc-02 runs were scored 9/10 for it. Module-level names bound once to a literal now count as constants; the Category 6 numbers here use the re-scored verdicts, and the first capture's golden verdicts were unchanged by the fix.
9. **Extended thinking varies output cost (Category 3).** Calls request `thinking={"type": "between_tools"}`, yet 72 of 288 turn and probe calls in the quality rerun emitted thinking tokens (up to 3,454 in one call), billed as output; 0 of 18 compactions did. The same turn's output cost therefore varies between repeats, and the per-turn output range above includes thinking.
10. **The first Category 3 capture hard-coded the compaction stop reason** (`"end_turn"` for every summariser call), so a truncated compaction could not be seen. *Fixed:* the live path records the API's real `stop_reason` for compactions, and the golden replays, rebuilt from the quality rerun, carry the recorded stop reason of every call.
11. **The Category 2 capture script wrote a constant stop reason** (`"end_turn"` for every drafted rung, and it rewrote stored templated rungs to `end_turn`), so a truncated draft could not be seen in the replays. *Fixed:* the capture script stores the API's `stop_reason` and no longer rewrites it, and the live path returns it on each rung result. The stored drafts were not re-captured, so they still carry the constant; their normal completion is inferred from text that ends cleanly and output below the cap.
12. **The Category 2 template requires an owner and a time window for every action item** (`action_plan` items: `owner` and `target_window` are required, exactly 3 items), even when the source gives none. Measured: the judge flagged an owner or deadline the source does not support in this many templated action items: Sonnet · section template + caps 8/12 (6 serious); Haiku · section template + caps 8/12 (6 serious). *Not changed:* the model-facing prompt and schema are as captured. Follow-up (not the app's template): one added sentence letting the template write "Not stated in source" cut serious errors per draft from 1.25 / 2.25 to 0.00 / 0.25 (Sonnet / Haiku, 12 fresh drafts each) and raised accuracy from 3.25 / 2.67 to 4.17 / 3.83, but actionability fell (3.67 / 3.25 → 3.08 / 2.67) and the long draft is still preferred in 15 of 16 comparisons. The app keeps the original template; the follow-up is shown beside it.
13. **The Category 4 capture script rejected answers with zero citations** (`capture_cat4_replays.py::_validate_rung`), which selects the recorded runs by outcome. *Fixed:* it now checks infrastructure only (every question answered and ended normally, cache written/read, reranker ran); the quality rerun kept every answer and found 0 zero-citation answers on the citation rungs.
14. **The Category 4 answer cap truncated answers.** At the app's `max_tokens=2048`, 3 of 64 pilot answers stopped on `max_tokens`, and the live path raises on truncation. In the rerun at 4,096, 5/192 answers used more than 2,048 output tokens (extended thinking included). *Fixed:* the app's synthesis cap is now 4,096 and real stop reasons are recorded.
15. **Category 4 BM25 is tuned to these questions.** `retriever.py` adds phrase bonuses for specific terms and values in the 8 test questions and Deccan's contracts, and the reranker prompt names the clauses the questions ask about, so BM25+rerank recall here is optimistic for unseen questions; with two look-alike suppliers added, it still dropped to the figures in the quality table.
16. **The Category 4 answer template invited absence claims** (found by the quality rerun). The synthesis prompt's last bullet asks for a "Required Sign-Off Gate: concrete operational, banking NOC, escrow, or delisting gate". With only 5 retrieved chunks in the prompt, answers filled that bullet by stating the documents contain no NOC or escrow gate. Of the 18 serious errors the grader reported on the two retrieval rungs with the original instructions, 18 claim the documents lack something they contain, and 9 of those concern the NOC/escrow gate (keyword count over `analysis/cat4_quality_rerun.json`). *Changed on 2026-11-26 for the retrieval versions:* the gate bullet now says to write "None stated in the text provided" when the text given states none, and a new line says that when something is not in the text provided, the answer should say so rather than say the documents or the deal room lack it. Measured effect (before → after, separate session sets): BM25 + Haiku rerank → 5 chunks + citations · 7 docs: answers saying the documents lack something 9 → 0, answers with a serious error 0 → 2, grader correctness 4.71 → 4.54, answers saying "not in the text provided" 2 → 21 (of 24); BM25 + Haiku rerank → 5 chunks + citations · 21 docs: answers saying the documents lack something 12 → 0, answers with a serious error 8 → 3, grader correctness 3.96 → 4.33, answers saying "not in the text provided" 10 → 22 (of 24); Haiku reranks the cached full corpus → 5 chunks + citations · 7 docs: answers saying the documents lack something 12 → 0, answers with a serious error 1 → 0, grader correctness 4.54 → 4.75, answers saying "not in the text provided" 1 → 21 (of 24); Haiku reranks the cached full corpus → 5 chunks + citations · 21 docs: answers saying the documents lack something 13 → 0, answers with a serious error 6 → 2, grader correctness 4.38 → 4.54, answers saying "not in the text provided" 6 → 20 (of 24). The full-corpus versions keep the original instructions and were not re-measured. The supplier-scope line the rerun puts in front of every question is now also in front of live and ad-hoc questions in the app.
17. **The Category 5 capture script selected runs by outcome.** `capture_cat5_replays.py::_validate_rung` re-captured a rung until its voucher matched exactly, evidence recall and tool precision were 100%, the hybrid rung escalated as "expected" and the naive rung used more than 25k prompt tokens. *Fixed:* it now rejects a run only for infrastructure failures (error status, a truncated last turn, no cache write/read on a cached rung). The golden replays were rebuilt from the ablation (repeat 0 of three versions, fixed mapping, not chosen by outcome).
18. **The old Category 5 rung 1 was a scripted prompt, not an unbounded loop.** It told Sonnet to run one raw `SELECT *` tool per step in a fixed 7-step order (max_tokens 2,048), so its turn count and cost were set by the script. *Fixed:* rung 1 now uses the ablation's free-choice protocol (several calls per turn allowed, 12-turn safety cap). Scripted vs free choice on the original invoices: inv-01 7.0 → 4 turns, -34% cost; inv-02 7.0 → 4 turns, -33% cost; inv-03 3.0 → 3 turns, +46% cost.
19. **The policy gate contradicts manual 2.1.** Its `WITHIN_1.5PCT_TOLERANCE` branch accepts any price up to 1.5% above the PO; the manual allows that band only when the PO's currency notes say the price is index-linked. On inv-06 every gated run (6/6) committed the gate's figures; runs without the gate matched the manual 12/12. *Found by the experiment, fixed on 2026-11-26* (gate `v2-manual-aligned`, after the recorded runs): the band now passes only when `purchase_orders.currency` says index-linked, otherwise the line pays the PO rate; the fixed gate equals the manual on inv-06; re-run on the fixed gate, 6/6 gated runs matched the manual. The recorded runs used the pre-fix gate, which is kept for replay only.
20. **The narrow query omits the PO currency notes.** `fetch_3way_match_bundle` does not return `purchase_orders.currency`, so a version that uses it cannot check manual 2.1's condition from the data; the raw-table tools return it. *Found by the experiment, fixed on 2026-11-26:* the bundle now also returns `purchase_orders.currency` (and the vendor `risk_flag`, any vouchers already posted for the invoice and each line's PO GST rate); every recorded run used the earlier bundle.
21. **The app's Category 5 runner stopped on `end_turn` turns that still held tool calls.** The API can return `stop_reason: end_turn` together with `tool_use` blocks; the runner ended the loop without executing them (one ablation record was superseded for the same harness failure). *Fixed:* every `tool_use` block in a non-truncated turn is executed and the loop continues; a turn cut off at max_tokens is recorded, not executed; the live path now uses max_tokens 4,096 and records the real stop reasons.
22. **Latent gate gaps not exercised by these invoices.** The gate ignored `approved_freight_waiver_inr` (manual 2.2/2.3 allow a freight waiver by amendment), took the GST rate from the first invoice line only, and did not implement Trigger 3 (duplicate invoice or a `PAYMENT_FREEZE` vendor). *Fixed on 2026-11-26* together with the band (not exercised by any recorded invoice, so the gate's output on the 11 pooled invoices is byte-identical): a signed amendment's freight waiver now raises the cap, GST is computed at each line's own PO rate when rates differ, and Trigger 3 hard-blocks a duplicate `invoice_id` or a `PAYMENT_FREEZE` vendor. The escalation-on-every-debit-note rule is unchanged. It also flags escalation for every debit note, including single-factor ones that manual 6.2 does not describe as multi-factor disputes.
23. **The Category 1 write-up rung is not a classifier.** Its prompt (unchanged) asks for a four-part analysis and never lists the allowed labels, so comparing its "accuracy" with the schema rung's mixes two tasks. The ablation adds the missing middle steps (the same classification asked as plain text, on both models) so each lever is measured on its own; the write-ups are reported as usability.
24. **Keyword scoring was unreliable in both directions.** On the same answers the app's regex extractor scored the plain-text classifications -14.3 / -14.3 pts (Sonnet / Haiku) against the reader model, and the write-ups +16.7 / +4.0 pts; on the 24 first-capture write-ups (most cut off at 2,048 tokens) it gave 27/42 and 24/42 where the reader model gave 23/42 and 22/42 (Sonnet / Haiku). *Fixed:* replayed write-ups are scored from the stored reader-model extraction; a live write-up is shown as not scored (the app has no reader model). `extract_prose_predictions` is kept for comparison.
25. **Stop reasons were not stored in the first Category 1 capture,** so its truncation (11/12 Sonnet and 8/12 Haiku write-ups at 2,048 output tokens) can only be inferred from output at the cap. *Fixed:* the golden replays now carry the API's stop reasons and thinking tokens, and the live path records them and flags truncation.
26. **Gemini Decision 1 answers different questions.** Its decision questions are not the JSON schema: priority comes from a 0–3 severity score, the category list omits `beauty_aerosol_sprays`, and the PII question is worded differently. Its rate ($0.10/M input, $0 output) is the repo's and not verified.
27. **The Batch API price is computed, not run.** Every "Batch" figure is the live run's tokens at 50%; no batch job was submitted.
28. **The first extraction pass hit the API usage limit.** 43 reader-model calls (the original-capture re-scoring and the schema-as-text check) failed with "API usage limit reached on 2026-11-26" and were completed on retry (43 ok); the failed records stay in `extractions.jsonl` as history, and only the latest ok record per call is used.

## Limitations

- Small samples: 12 items (Category 1; 3 runs each per version, 36 runs per version), 4 documents; Category 5 has 12 invoices (33 pooled runs per version: 11 invoices × 3 repeats, plus 3 runs per version on the gate-disagreement invoice); Category 4 has 24 answers per rung and corpus size (8 questions × 3 sessions); Category 3 has 6 sessions per rung (2 scenarios × 3 repeats) and Category 6 has 15 runs per arm (3 incidents × 5 repeats). Treat percentages as indicative, not statistically robust.
- Category 1 ground truth covers 42 fields per repeat (4 per ticket, 3 per SKU); the other schema fields (reason code, PII categories, hazmat class, material) are not scored. Free-text answers were read by one reader model (`claude-opus-5-5`, not under test) in one pass; its check on 20 JSON answers rewritten as text agreed on every field, but no second reader or human cross-checks it. Half the items (the six batch items) are short: their write-up prompts are 261–336 tokens against 1,245–1,468 for the six presets, so pooled token ranges mix two item sizes.
- Category 6 ceiling effect: every arm verified 15/15, so these incidents are too easy to show a quality difference between context designs, and CpO equals cost per run in every arm.
- Category 2 now has a quality measurement: a deterministic fact key plus a single blind LLM judge (`claude-opus-5-5`; rubric with 3 passes per draft and position-swapped head-to-head comparisons) on one draft per rung per document (12 drafts). Judge repeats measure judge noise, not drafting variance, and no second judge or human grading cross-checks the judge's taste; the lead hand-verified the serious errors against the sources.
- Category 3 now has a quality measurement: a fixed answer key scored by deterministic string matching (no LLM judge). It checks whether specific IDs, amounts and dates survive, not whether an answer is helpful, and the recall questions are 6 per scenario (12 in all), each asked once per session.
- Category 4 quality: one blind-grader pass per answer (`claude-opus-5-5`, not a model under test) plus a deterministic answer key; 8 questions on one deal room; the larger corpus adds two synthetic look-alike suppliers generated by a deterministic transform of Deccan's documents, not real contracts. Grader noise was not measured (no repeat grading) and no human graded the answers; the lead checked the serious errors' source quotes against the documents.
- Category 4 answer-format change: measured on the retrieval versions only (the full-corpus versions were not re-run with it), and before and after are separate session sets (3 sessions of 8 questions per version and corpus size each), so the before → after differences include session-to-session variation.
- Several rungs change more than one lever at once (e.g. model + template in Category 2), so savings cannot be attributed to individual levers. Category 5's ablation adds its levers one at a time, except that adding the policy gate also changes the tool set, the prompt and the turn cap.
- Category 5 ceiling effect: every version scored at or near 100% exact vouchers (32–33 of 33), so accuracy differences between versions cannot be detected; the invoices test simple arithmetic (quantities × rates, an 18% GST split, a debit note), and one invoice (inv-06) is where the policy gate and the manual disagree.
- The deck's daily-volume claim (Category 6: 1.5M–10M tokens/dev/day) and its production-scale framing can't be checked from single runs.
